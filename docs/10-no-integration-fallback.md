# 10 — No-Integration Fallback

> Assume, correctly, that **no organization will have integrated** when the first user signs up. If PRM
> only works against integrated counterparties, it never gets a first user. This section is therefore
> not a fallback — for the first two years it is the **primary** path.

## 1. What PRM produces without any cooperation

Even against a wholly unresponsive organization, the user ends up holding:

1. A **signed policy** with a verifiable timestamp predating the interaction.
2. A **delivery record** with third-party-attested transport evidence.
3. A **ledger entry** chaining the two, included in a timestamped transparency log.
4. A **non-response record** after the statutory or stated response window elapses.

That bundle is the deliverable. It supports a records complaint, a regulator filing, a public-records
advocacy campaign, a demand letter, or discovery. It does not require the organization's participation
— and that independence is precisely why it has leverage.

## 2. Delivery channels, strongest evidence first

| Channel | Evidence produced | Strength |
|---|---|---|
| **Certified mail, return receipt** | USPS tracking + signed green card, scanned and hashed into the ledger | Strongest; legally routine; often statutorily sufficient for notice |
| **Statutory privacy-request web form** | Screenshot + submission confirmation + reference number, all hashed | Strong — many jurisdictions require these forms to exist |
| **Email to a published privacy/records address** | DKIM-signed outbound copy, `Message-ID`, SMTP 250 receipt, and any DKIM-signed auto-reply | Good; DKIM signatures make an inbound reply independently verifiable |
| **In-person / counter delivery** | Signed paper acknowledgment, photo, timestamp, geolocation (optional, user-controlled) | Good, situational |
| **QR card handed over** | Ledger entry + card serial + optional counterpart signature | Weak alone; strong combined with a follow-up email |

**The DKIM detail is worth engineering for.** If a municipality's mail server DKIM-signs its auto-reply,
that reply is a *cryptographically verifiable admission of receipt from their own domain*. Preserve the
raw MIME with headers intact and hash it into the ledger — a re-serialized or "cleaned" copy destroys
the signature. Store raw `.eml`, always.

## 3. The notice packet

One artifact the user sends. Generated by the app, assembled server-side, signed client-side.

```
prm-notice-2026-09-06-breezypoint.pdf
├── p1  Cover letter — plain language, names the recipient, states the request,
│       cites applicable statute if the user selected a jurisdiction template
├── p2  The policy, rendered from humanReadable (the signed prose)
├── p3  Rights matrix as a readable table
├── p4  How to verify this document (URL, digest in hex, npx one-liner, QR)
└── attachments/
    ├── policy.json          the signed bytes
    ├── proof.prmproof       inclusion proof + STH + RFC 3161 token + KEL
    └── verify.txt           step-by-step verification with openssl and npx
```

Design constraints learned from how these documents actually get handled:

- **One page of prose maximum** before the substance. Records clerks triage by length.
- **No legal threats in the cover letter.** A notice that reads as a demand gets routed to legal and
  dies; one that reads as a records request gets processed.
- **Print-safe.** It will be printed, scanned, and re-filed. Digest in hex, in a monospace box, large
  enough to survive a fax. Yes, still fax.
- **Name a specific response mechanism** — an email address the user monitors and a reference number.

## 4. Recording a response (or the absence of one)

```
notice.sent      → digest of the packet, channel, recipient, timestamp, tracking number
notice.delivered → digest of the transport evidence (green card scan, SMTP receipt, form confirmation)
acknowledgment.received → digest of their reply; if it's a signed receipt, verify and store the proof
dispute.raised   → user's response to a refusal or partial compliance
```

**Non-response is an event.** After the response window (user-set, defaulting to the jurisdiction
template's statutory period), the app writes an `acknowledgment.received` entry with
`disposition: "none"` and the elapsed period. A timestamped, log-included record that *no response was
received within N days* is evidentially useful and costs nothing to produce.

Automate the follow-up: a Vercel Cron job checks for elapsed windows and prompts the user to send a
second notice — never sending automatically. Automated sending would turn the product into a harassment
tool and would destroy its credibility with the recipients it needs to persuade.

> **Decision — the human is always in the loop for outbound delivery.**
> *Why:* an automated notice cannon is a nuisance-mail generator and a liability. *Threat:* PRM being
> characterized as a harassment service; recipients blocking the domain wholesale. *MVP:* yes — one-tap
> send, never scheduled send. *Standard:* n/a. *Simpler alternative:* none worth having.

## 5. Evidence preservation

- Artifacts (scans, `.eml`, screenshots, PDFs) are stored **encrypted client-side** with `K_vault` and
  uploaded as ciphertext to Vercel Blob. PRM cannot read them.
- Only digests go into ledger entries, and only leaf hashes reach the log.
- An **evidence export** produces a single ZIP: artifacts, ledger, proofs, and a `MANIFEST.txt` with
  every digest and verification instructions. This is the thing a user hands to a lawyer.
- Retention is the user's choice, defaulting to indefinite. Deleting evidence is deleting their own
  case; the UI must say that in those words.

## 6. Honest limits

Say these plainly in the product, not just the docs. Overclaiming here is how a project like this loses
credibility with exactly the people it needs.

- PRM does not compel anyone to do anything. It creates notice and evidence.
- A policy is **not** a contract. The recipient never agreed to it. Its force comes from statute,
  regulator attention, litigation posture, and public accountability — not from PRM.
- Some processing is lawful over the person's objection. The `basisAcknowledged` field exists so users
  can state their position accurately rather than making claims that are easy to dismiss wholesale.
- The realistic near-term value is **documented, timestamped, verifiable notice at scale** — which is
  genuinely new, and is enough.
